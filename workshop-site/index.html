Hands-on lab · OpenTelemetry Java Contrib · Splunk Observability Cloud

IBM MQ observability with OpenTelemetry Java Contrib

Clone this repo, run IBM MQ locally, export queue metrics with OpenTelemetry Java Contrib ibm-mq-metrics, and view ibm.mq.* metrics, APM traces, and structured logs in Splunk Observability Cloud.

Everything you need is in this repo

Docker Compose stack (MQ, Java exporter sidecar, OTel collector, instrumented sample apps), config files, and this guided site. Unlike the main mq_otel workshop, this lab includes hands-on APM exercises out of the box.

Application architecture — what the demo does

This lab simulates a simple order pipeline: a web API accepts orders, checks inventory, publishes to IBM MQ, and a background worker fulfills them. Every hop is instrumented with OpenTelemetry so Splunk APM can draw a meaningful service map.

Order lifecycle (one request)

  1. You (or load-traffic.sh) send POST /orders to order-producer with productId, quantity, and optional X-Correlation-Id.
  2. order-producer calls inventory-service → POST /check to confirm enough stock exists. If not, the order is rejected with 409 and nothing is sent to MQ.
  3. order-producer publishes a JSON order message to IBM MQ queue ORDER.REQ and returns 202 accepted.
  4. order-consumer (running in the background) reads the message from ORDER.REQ.
  5. order-consumer calls inventory-service → POST /fulfill to decrement in-memory stock for that SKU.

Async messaging vs one long trace

Producer and consumer run as separate processes connected by IBM MQ. Splunk APM typically shows two trace trees per order (one for the HTTP request at the producer, one for the background GET at the consumer), not a single end-to-end trace. Tie them together with the shared orderId / X-Correlation-Id in span attributes and structured logs (Steps 9 and 11). Optional Step 10 (MQ tracing exit) can add queue-manager spans that sit between producer and consumer in the map.

Why add inventory-service?

A producer → MQ → consumer map alone can look like a thin line. The inventory calls add realistic HTTP dependencies on both sides of the queue so the service map shows a hub-and-spoke pattern: two services talking to a shared downstream API, with MQ in the middle.

Step 1~5 min

Prerequisites

  • Docker Desktop (or Docker Engine + Compose v2)
  • Git
  • Splunk Observability Cloud ingest token (facilitator-provided or your org’s token)
  • Node.js 20+ (optional — not required; traffic script uses curl)

Apple Silicon: services use linux/amd64. The Java metrics image downloads prebuilt JARs from Maven Central (no Gradle compile).

Step 2~2 min

Clone the repo

Terminal
git clone https://github.com/garrett-splunk/MQ-Java-Otel-Workshop.git
cd MQ-Java-Otel-Workshop
Step 3~5 min

Splunk Observability Cloud token

Terminal
cp .env.splunk.example .env.splunk

Replace your-ingest-token-here with your ingest token. Match SPLUNK_REALM and URLs to your org (us1, eu0, etc.). Never commit .env.splunk.

grep -q 'your-ingest-token-here' .env.splunk && echo "WARN: replace placeholder token" || echo "OK: token line edited"
Step 4~2 min

Lab environment

Terminal
cp .env.example .env

Default demo MQ password is passw0rd (MQ_APP_PASSWORD in .env). The Java exporter uses the same credentials via Compose environment variables.

OTEL_SDK_DISABLED=false (default) turns on OTLP traces and logs from order-producer, inventory-service, and order-consumer for the APM exercises in Step 9. Set true only if you want metrics-only locally.

Start the stack

Builds and starts: IBM MQ, OpenTelemetry Collector, ibm-mq-java-metrics sidecar, order producer/consumer, inventory service, and the local workshop site.

Step 9~15 min

APM — trace an order through IBM MQ

Sample apps emit OpenTelemetry traces for HTTP requests and MQ PUT/GET operations. The collector forwards them to Splunk Observability Cloud APM via the traces pipeline (otlphttp/traces exporter). For a full picture of which services call which, read Application architecture first.

9a — Trigger a traceable order

Use a unique correlation ID so you can find the same request in APM and logs:

Terminal
CORR_ID="apm-lab-$(date +%s)"
curl -v -X POST http://localhost:8080/orders \
  -H "Content-Type: application/json" \
  -H "X-Correlation-Id: ${CORR_ID}" \
  -d '{"productId":"SKU-APM","quantity":1}'
echo "Correlation ID: ${CORR_ID}"

Expect 202 accepted. The producer calls inventory-service to verify stock, then creates a span named mq.put.order; the consumer creates mq.get.order when it reads the message and calls inventory again to fulfill the order.

9b — Confirm traces reach the collector

Terminal
curl -s http://localhost:13133/metrics | grep 'otelcol_receiver_accepted_spans' | head -5

The counter should increase after each order. Allow ~30s for batch export to Splunk.

9c — Find traces in Splunk Observability Cloud APM

  1. Open APM → Services (or Traces).
  2. Set environment filter: deployment.environment:ibm-mq-lab
  3. Locate services order-producer, inventory-service, and order-consumer.
  4. Open Traces for order-producer; look for spans POST /orders, inventory.check, and mq.put.order.
  5. Inspect attributes: messaging.system=ibmmq, messaging.destination.name=ORDER.REQ, order.product_id.
  6. Open traces for order-consumer and find mq.get.order and inventory.fulfill spans.
  7. Open the Service map — you should see order-producer → inventory-service, producer → IBM MQ → consumer, and consumer → inventory-service (plus MQ tracing exit spans if enabled).

Correlation ID

The HTTP header X-Correlation-Id becomes the order ID in the message payload and appears in structured logs. Search logs (Step 11) with the same ID to tie metrics, traces, and logs together.

9d — Generate more trace volume

Terminal
npm run load-traffic -- 15 500
Step 10~10 min · optional

IBM MQ native tracing exit (optional)

IBM MQ 9.3+ can emit additional OpenTelemetry spans from inside the queue manager via a tracing user exit. This is separate from app spans and Java Contrib metrics.

Config is already mounted by the mq-tracing-setup service (mq/mqtracingexit.conf → OTLP gRPC otel-collector:4317). Restart MQ to load it:

Terminal
bash scripts/mq-tracing-enable.sh
# wait ~60s, then send another order (Step 9a)

In APM, look for additional spans originating from MQ internal operations alongside mq.put.order / mq.get.order. Support varies by MQ platform version — treat as a bonus exercise if spans appear.

Step 11~5 min · optional

Structured logs in Splunk Observability Cloud

Producer and consumer emit JSON logs via OTLP to the collector logs pipeline (splunk_hec/o11y exporter).

  1. Open Log Observer (or Logs).
  2. Filter: deployment.environment:ibm-mq-lab
  3. Search: service.name:order-producer, service.name:inventory-service, or service.name:order-consumer
  4. Find log lines like Order message published to IBM MQ / Order message consumed from IBM MQ.
  5. Match the correlationId field from Step 9a across producer and consumer logs.

Troubleshooting

SymptomThings to check
mq exits with code 1 / AMQ5776E Stale queue manager volume from a failed first start. Run docker compose down -v, git pull, rebuild mq, then docker compose up -d again.
ibm-mq-java-metrics build fails Needs outbound HTTPS to Maven Central during docker compose build. On Apple Silicon, image uses linux/amd64 emulation.
MQ auth errors in Java logs Channel MQOTEL.SVRCONN in mq/20-lab-connect.mqsc; password matches MQ_APP_PASSWORD in .env.
No ibm.mq in Splunk .env.splunk token; collector on :13133; wait 1–2 scrape intervals (15s) plus batch (5s).
No traces in APM Confirm OTEL_SDK_DISABLED=false in .env, then docker compose up -d --force-recreate order-producer order-consumer inventory-service. Check collector: Step 9b. Wait 30–60s after traffic.
503 Inventory service unavailable curl http://localhost:8082/health — ensure inventory-service is running. Producer waits for inventory before MQ PUT.
409 Insufficient inventory Expected if stock is exhausted for a SKU. Restart inventory-service to reset in-memory stock, or use another productId (e.g. SKU-100).
Services missing in APM Environment filter must be ibm-mq-lab. Send at least one successful order before searching.
verify-stack.sh fails on Java container docker compose logs ibm-mq-java-metrics — container may still be building on first start.
